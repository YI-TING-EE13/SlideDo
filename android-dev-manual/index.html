開發環境設定

Android 開發最常見的卡關點，是 JDK、SDK、Gradle、ADB 版本或路徑不一致。

必要工具

工具 用途 SlideDo 目前需求
Android Studio 開啟專案、Sync Gradle、建立模擬器、執行 App、查看 Logcat。 建議安裝目前穩定版。
Android SDK 提供 compile SDK、platform tools、build tools、emulator。 compileSdk 36，裝置需 API 26+。
JDK / JBR Gradle 與 Java 編譯需要。 Java 17；若系統 JDK 太新，可用 Android Studio 內建 JBR。
Gradle Wrapper 使用專案指定的 Gradle 版本，不依賴全域安裝。 android/gradlew.bat 指向 Gradle 8.14.5。
ADB 列出裝置、安裝 APK、啟動 Activity、讀取裝置 log。 由 Android SDK Platform Tools 提供。

Android Studio 初次設定

  1. 安裝 Android Studio。
  2. 開啟 SDK Manager，確認已安裝 Android SDK Platform 36。
  3. 在 SDK Tools 勾選 Android SDK Platform-Tools、Android SDK Build-Tools、Android Emulator。
  4. 開啟 Device Manager，建立 Pixel 系列模擬器，例如 Pixel 7 或 Pixel 8。
  5. 選擇 Google APIs x86_64 或 arm64 系統映像，API 35 或 API 36 都可用於此專案測試。
  6. 第一次開啟專案時，選擇 SlideDo/android 這個資料夾，而不是整個 repo 根目錄。
路徑重點

SlideDo 有根目錄 Gradle 專案，也有 android/ 子專案。 Android Studio 要開 Android App 時，建議開 android/，這樣 IDE 會以 SlideDoAndroid 專案同步 app module。

命令列環境檢查

在 Windows PowerShell 或 Command Prompt 中執行：

java -version
android\gradlew.bat -p android --version
adb version
adb devices

如果 Gradle 因 Java 版本相容性失敗，可暫時使用 Android Studio 內建 JBR：

set JAVA_HOME=C:\Program Files\Android\Android Studio\jbr
set PATH=%JAVA_HOME%\bin;%PATH%
cd android
gradlew.bat :app:assembleDebug

新手應理解的環境名詞

SDK
Software Development Kit。Android SDK 提供編譯、模擬器、裝置工具與平台 API。
JDK
Java Development Kit。用來編譯 Java 程式與執行 Gradle。
JBR
JetBrains Runtime。Android Studio 內建的 Java runtime，通常與 IDE / Gradle 相容性較好。
ADB
Android Debug Bridge。電腦與 Android 裝置溝通的命令列工具。
AVD
Android Virtual Device。Android Studio 建立的模擬器裝置設定。

從零初始化一個 Android App

這一章用「如果今天要從零建立 SlideDo Android」的角度說明。

用 Android Studio 建立新專案

  1. 開啟 Android Studio，選擇 New Project。
  2. 若用 Java 入門，可選 Empty Views Activity 或 No Activity 後自行建立 Activity。
  3. 輸入 App 名稱，例如 SlideDo。
  4. Package name 設為反向網域格式，例如 com.klotski.android。
  5. Language 選 Java。
  6. Minimum SDK 選 API 26 或更高，符合本專案目前設定。
  7. 建立後等待 Gradle Sync 完成。

新專案最小檔案

一個原生 Android App 至少會有：

檔案 用途
settings.gradle 宣告專案名稱、module、plugin repository。
build.gradle 宣告 Android Gradle Plugin 版本與全域建置設定。
app/build.gradle 宣告 app 的 namespace、applicationId、SDK 版本、source set、依賴。
AndroidManifest.xml 宣告 App、Activity、權限、launcher 入口。
MainActivity.java App 第一個畫面與主要互動入口。
res/values/strings.xml 集中管理畫面文字，方便修改與多語系。

SlideDo 的特殊初始化策略

SlideDo 不是把所有程式碼都寫在 Android module 裡。它把共用遊戲規則保留在根目錄 src/com/klotski/core，Android module 再透過 Gradle source set 把這些 Java 檔案納入編譯。 這讓桌面版與 Android 版共用同一套規則。 

android {
    namespace "com.klotski.android"
    compileSdk 36

    defaultConfig {
        applicationId "com.klotski.android"
        minSdk 26
        targetSdk 36
        versionCode 1
        versionName "1.0"
    }

    sourceSets {
        main.java.srcDirs += ["../../src/com/klotski/core"]
    }
}
入門建議

如果你是完全新手，第一個 App 可以先不要共用桌面核心，直接在 Android module 裡完成一個小功能。 等你熟悉 Activity、View、Gradle、資源檔與 Logcat 後，再學 SlideDo 這種共用核心架構。

Android 主要檔案責任

檔案 責任 新手修改建議

Manifest 入口

Android 透過 manifest 找到可從桌面啟動的 Activity：

<activity
    android:name=".MainActivity"
    android:exported="true">
    <intent-filter>
        <action android:name="android.intent.action.MAIN" />
        <category android:name="android.intent.category.LAUNCHER" />
    </intent-filter>
</activity>

src/com/klotski/ui 是桌面 Swing UI； android/app/src/main/java/com/klotski/android 才是 Android UI。 遊戲規則在 src/com/klotski/core，兩端都應共用它。

Gradle 基礎

Gradle 是 Android 專案的建置系統。新手不必一次學完，但一定要懂常用檔案與任務。

Gradle 在 Android 中負責什麼

  • 下載 Android Gradle Plugin 與第三方依賴。
  • 讀取 source set，知道哪些 Java / Kotlin / resource 檔案要編譯。
  • 把 Java 程式碼、Android resource、manifest 打包成 APK。
  • 執行單元測試、lint、assembleDebug、assembleRelease 等任務。
  • 和 Android Studio Sync，讓 IDE 知道專案設定。

SlideDo Android Gradle 檔案

檔案 重點
android/settings.gradle 宣告 repository 來源、root project name、include :app。
android/build.gradle 宣告 Android Gradle Plugin 版本：com.android.application。
android/app/build.gradle 宣告 namespace、applicationId、SDK、Java 17、共用 core source set。
android/gradle/wrapper/gradle-wrapper.properties 鎖定 Gradle 8.14.5。團隊成員用 wrapper 就會拿到一致版本。

常用 Gradle 任務

cd android
gradlew.bat :app:assembleDebug
gradlew.bat :app:lintDebug
gradlew.bat :app:clean
gradlew.bat tasks

根目錄測試與 Android 子專案的差異

SlideDo 根目錄 build.gradle 是 Java / JUnit 測試設定，主要測 src/com/klotski/core。Android app 的建置則在 android/。 因此你會看到兩種常用命令： 

android\gradlew.bat -p . test
cd android
gradlew.bat :app:assembleDebug
Gradle Sync 失敗時先看三件事

第一，Android SDK 是否安裝到正確位置。第二，JDK 是否與 Android Gradle Plugin 相容。 第三，網路是否能下載 Gradle wrapper 與 plugin dependencies。

架構模式與分層思維

架構不是為了複雜，而是為了讓修改範圍可控。

SlideDo 目前的實際架構

Core Layer

GameModel、Direction、Solver、SaveManager。負責規則、狀態、求解器與桌面保存格式。

Android Controller Layer

MainActivity。負責畫面切換、按鈕、dialog、保存、紀錄、solver 執行緒。

Android Rendering Layer

KlotskiView。負責棋盤繪製、手勢、動畫、busy state。

Resource Layer

res/values/strings.xml、styles.xml、drawable/。負責文字、主題與圖示。

目前不是完整 MVVM，這是合理的

SlideDo Android 目前使用單一 Activity，透過 Screen enum 管理簡單畫面狀態： 

private enum Screen {
    HOME,
    MODE_SELECT,
    HOW_TO_PLAY,
    RECORDS,
    GAME
}

對小型 App 或學習專案來說，這比一開始就導入 ViewModel、Repository、Navigation Component 更容易理解。 但隨著功能增加，應考慮逐步拆分：

現在的做法 何時會吃力 可演進方向
單一 MainActivity 建所有畫面 Settings、Results、Tutorial、排行榜都變複雜時 拆出 screen builder class，或改用 Fragment / Navigation。
SharedPreferences 存全部狀態 資料型態變多、需要歷史紀錄或同步時 改用 DataStore 或 Room。
Java programmatic UI 畫面越來越多，樣式難以重用時 XML layout、custom components，或 Jetpack Compose。
Activity 直接管理 solver thread 背景工作變多、需要取消與生命週期保護時 Executor、ViewModel、WorkManager 或 coroutine-based 架構。

最重要的架構原則

  • 不要在 Android UI 重寫遊戲規則：規則只放在 GameModel。
  • 不要讓 View 決定產品流程：KlotskiView 只管棋盤與手勢，畫面流程由 MainActivity 管。
  • 不要讓背景工作阻塞主執行緒：solver 在背景 thread 跑，結果再 post 回主執行緒。
  • 保存資料要包含恢復所需欄位：尺寸、目前格子、初始格子、步數、 elapsed time 都要保存。
  • 功能先寫 acceptance criteria：例如「whole-line slide 只算一步」、「solver 輔助勝利不覆寫紀錄」。

如何寫功能 acceptance criteria

新功能不要只寫「新增 Settings」。要寫清楚使用者怎麼驗證它完成：

Feature: Haptics Setting

Acceptance criteria:
- Settings screen has a haptics toggle.
- Default is enabled.
- Turning it off stops board and win haptic feedback.
- The choice persists after app restart.
- The setting does not affect game save/load state.
規劃順序

對新手來說，最好的順序通常是：使用者流程 → 畫面草圖 → 狀態欄位 → 程式責任 → 測試清單。 直接寫程式很快，但後期最容易迷失。

畫面與互動開發

SlideDo 的 Android UI 展示了 Activity 建畫面、自訂 View 畫棋盤、觸控事件與動畫。

Activity 負責畫面組裝

MainActivity 的 onCreate 會建立初始模型、註冊返回行為、顯示 Home，並啟動每秒更新 HUD 的 ticker：

@Override
protected void onCreate(Bundle savedInstanceState) {
    super.onCreate(savedInstanceState);
    getWindow().setStatusBarColor(COLOR_BACKGROUND);
    getWindow().setNavigationBarColor(COLOR_BACKGROUND);

    int lastSize = getSharedPreferences(PREFS, MODE_PRIVATE).getInt(KEY_LAST_SIZE, 4);
    attachModel(new GameModel(lastSize));
    registerBackHandler();
    showHomeScreen();
    handler.post(ticker);
}

自訂 View 負責棋盤

KlotskiView 繼承 View，覆寫 onDraw 畫棋盤， 覆寫 onTouchEvent 偵測點擊與滑動。這種做法適合棋盤、圖表、遊戲、繪圖工具等需要精準繪製的畫面。 

public boolean onTouchEvent(MotionEvent event) {
    if (model == null) {
        return true;
    }

    switch (event.getActionMasked()) {
        case MotionEvent.ACTION_DOWN:
            if (isBusy() || model.isSolved()) {
                clearTouchState();
                return true;
            }
            downX = event.getX();
            downY = event.getY();
            return true;
        case MotionEvent.ACTION_UP:
            if (isBusy() || model.isSolved()) {
                clearTouchState();
                return true;
            }
            // Small movement is treated as tap; larger movement is treated as swipe.
            return true;
        default:
            return true;
    }
}

Programmatic UI 與 XML Layout 的取捨

方式 優點 缺點 適合情境
Programmatic UI 流程集中、動態產生容易、適合學習 View API。 大型畫面可讀性下降，設計預覽較弱。 小型 app、prototype、自訂畫面多。
XML Layout 結構清楚、可預覽、資源化較自然。 動態畫面需搭配 binding 或 findViewById。 傳統 Android app、多畫面表單與清單。
Jetpack Compose 宣告式 UI、狀態驅動、現代 Android 主流方向。 需學 Compose 思維，和 Java 專案整合不如 Kotlin 自然。 Kotlin 新專案、快速迭代 UI。

Android UI 實務注意事項

  • 觸控目標建議至少約 48dp，避免按鈕太小。
  • 長文字要允許換行，不要讓 status 或按鈕文字互相覆蓋。
  • 動畫期間要鎖住輸入，避免同時修改模型造成狀態錯亂。
  • 背景工作完成後，更新 UI 必須回到主執行緒。
  • 支援返回鍵時，要想清楚每個畫面的返回目的地。
  • 自訂 View 要實作 performClick()，讓 accessibility click dispatch 有基本支援。
  • 旋轉、背景、回前景都要測，因為 Activity 生命週期會影響狀態保存。

資源管理

Android resource 系統讓文字、圖示、顏色、尺寸、語系與主題可以和程式碼分離。

SlideDo 目前的 resource

路徑 用途
android/app/src/main/res/values/strings.xml App 名稱、Home、Mode Select、How to Play、Records、Game、dialog、toast、button 文字。
android/app/src/main/res/values/styles.xml App theme、font family、navigation bar color、accent color。
android/app/src/main/res/drawable/ic_launcher.xml Launcher icon。

為什麼文字要放在 strings.xml

<string name="home_continue">Continue</string>
<string name="mode_title">Choose a Size</string>
<string name="button_restart">Restart</string>

好處是：

  • 文字集中，修改時不用在 Java 檔案到處找。
  • Android lint 可以提醒硬編碼文字。
  • 未來要支援繁體中文、英文、日文時，可以建立 values-zh-rTW/strings.xml。
  • 格式化字串可以安全帶入參數，例如 %1$dx%2$d Puzzle。

資源命名習慣

  • 用畫面或用途當 prefix，例如 home_、mode_、dialog_。
  • 按鈕文字可用 button_ prefix。
  • 同一組文字不要同時寫在 Java 和 XML，避免後續不同步。
  • 圖片與 icon 使用小寫加底線，例如 ic_launcher。
目前可改善點

SlideDo 的部分顏色常數目前寫在 MainActivity。小專案這樣可接受， 但若要建立主題切換或設計系統，建議把顏色移到 colors.xml，尺寸移到 dimens.xml。

狀態管理與資料保存

Android App 最容易出錯的地方之一，是使用者離開、旋轉或重新開啟後狀態不見。

SlideDo 目前保存哪些資料

MainActivity 使用 SharedPreferences，保存：

  • size：棋盤尺寸。
  • grid：目前棋盤。
  • initial_grid：本局初始棋盤，Restart 需要。
  • moves：步數。
  • elapsed：已花時間。
  • last_size：上次選擇尺寸。
  • best_3_moves、best_3_time 等：各尺寸最佳紀錄。

保存時機

當 Activity 進入背景時，onPause() 會保存遊戲：

@Override
protected void onPause() {
    super.onPause();
    saveGame();
}

保存內容會從 GameModel 取出可恢復狀態：

SharedPreferences.Editor editor = getSharedPreferences(PREFS, MODE_PRIVATE).edit();
editor.putInt(KEY_SIZE, model.getSize());
editor.putString(KEY_GRID, flatten(model.getGridCopy()));
editor.putString(KEY_INITIAL_GRID, flatten(model.getInitialGridCopy()));
editor.putInt(KEY_MOVES, model.getMoveCount());
editor.putLong(KEY_ELAPSED, elapsed);
editor.apply();

什麼情境用 SharedPreferences

資料類型 適合 SharedPreferences 嗎 更進階選項
設定開關、上次選項、小量狀態 適合 DataStore
一筆小型遊戲存檔 可接受 DataStore 或 JSON file
大量排行榜、歷史紀錄、關卡資料 不適合 Room database
圖片、音效、二進位檔 不適合 App-specific files

生命週期基本概念

onCreate()
Activity 初次建立，通常初始化 UI 與狀態。
onPause()
畫面即將失去焦點，是保存輕量狀態的好時機。
onResume()
畫面回到前景，可恢復感測器、動畫、刷新狀態。
Configuration change
例如旋轉螢幕，可能導致 Activity 重建。新手一定要測。

共用遊戲核心與 Android 的分工

SlideDo 最值得學習的一點，是把遊戲規則和 Android 畫面拆開。

核心規則

  • 空格是 0。
  • 完成狀態是 row-major 順序，0 在最後一格。
  • Direction 表示空格移動方向，不是數字 tile 的移動方向。
  • GameModel.move(Direction) 是單步移動。
  • GameModel.slideLineTo(row, col) 是整列或整欄滑動，一次手勢只算一步。
  • Restart 回到 initialGrid，不是重新亂數洗牌。
  • solver 輔助完成不能覆寫玩家最佳紀錄。

整列滑動的核心範例

public boolean slideLineTo(int row, int col) {
    if (!isGameRunning || !isValid(row, col) || (row == emptyRow && col == emptyCol)) {
        return false;
    }

    Direction dir;
    int steps;
    if (row == emptyRow) {
        dir = col < emptyCol ? Direction.LEFT : Direction.RIGHT;
        steps = Math.abs(col - emptyCol);
    } else if (col == emptyCol) {
        dir = row < emptyRow ? Direction.UP : Direction.DOWN;
        steps = Math.abs(row - emptyRow);
    } else {
        return false;
    }

    undoStack.push(copyGrid(grid));
    for (int i = 0; i < steps; i++) {
        moveInternal(dir, false, false, false, false);
    }

    moveCount++;
    notifyLineMove(dir, steps);
    notifyGridChanged();
    checkWin();
    return true;
}

Observer 模式

GameModel 不知道 Android View 怎麼畫，也不知道 Swing UI 怎麼畫。 它只通知觀察者發生了什麼：

  • onGridChanged()：棋盤狀態變了。
  • onMove(Direction dir)：單步移動發生。
  • onLineMove(Direction dir, int steps)：整列或整欄滑動發生。
  • onGameWon(int moves, long timeMs)：遊戲完成。

Solver 實務

BFS、A*、IDA* 都可能耗時。Android UI thread 不能被長時間阻塞，所以 MainActivity 會開背景 thread 執行 solver，完成後再用 Handler 回到主執行緒更新 UI。 

new Thread(() -> {
    List<Direction> solution = solver.solve(model);
    handler.post(() -> finishSolver(solver, solution));
}, "SlideDoSolver").start();
新手常犯錯

不要為了 Android 觸控方便，在 KlotskiView 裡自己改二維陣列。 任何棋盤變化都應該透過 GameModel，否則 undo、save、records、solver 很容易全部失準。

實機、模擬器與測試流程

Android 測試需要同時考慮程式規則、畫面行為、裝置差異與生命週期。

測試層級

測試類型 SlideDo 目前做法 適合驗證
Unit Test test/com/klotski/core 的 JUnit 測試。 遊戲規則、save/load、solver 基本行為。
Lint :app:lintDebug。 Android API、resource、可用性、潛在錯誤。
Manual Smoke Test 在 emulator 或 device 手動操作。 Home、Mode Select、手勢、旋轉、保存、dialog。
Instrumentation Test 尚未建立，是後續高優先項目。 自動化點擊、畫面導航、Activity 行為。

建立模擬器

  1. Android Studio 開啟 Device Manager。
  2. 選擇 Pixel 7 或 Pixel 8。
  3. 系統映像選 Google APIs API 35 或 36。
  4. 啟動後執行 adb devices，應看到 emulator-5554 device 類似輸出。

實機測試設定

  1. 手機開啟 Developer options。
  2. 啟用 USB debugging。
  3. USB 連接電腦後，手機上允許這台電腦偵錯。
  4. 執行 adb devices，確認裝置狀態是 device 而不是 unauthorized。

SlideDo Android 手動 smoke test

  • 啟動 App，確認進入 Home，不是直接進入棋盤。
  • 從 Home 開 How to Play，返回後仍在正確畫面。
  • 從 New Game 進 Mode Select，分別啟動 3x3、4x4、5x5。
  • 點擊相鄰且對齊空格的 tile，步數增加一。
  • 點擊同列或同欄但非相鄰 tile，整列滑動且步數只增加一。
  • 整列滑動後按 Undo，整個手勢一次復原。
  • Restart 後步數與時間重置，棋盤回到本局初始狀態。
  • Menu 裡 Save，Restart 後 Load，確認棋盤、步數、時間、初始棋盤可恢復。
  • Assist 中在 4x4 開 BFS，確認昂貴操作警告出現。
  • 背景 App 後再回來，確認 autosave 有保留目前棋盤。
  • 旋轉螢幕後回到直向，確認狀態沒有遺失。
測試不是只看有沒有 crash

對遊戲 App 來說，還要看步數是否正確、動畫期間是否鎖 input、保存是否完整、返回鍵是否合理、 solver 是否阻塞 UI、輔助完成是否污染玩家紀錄。

Logcat 使用與除錯方式

Logcat 是 Android 開發最重要的除錯工具之一。

在 Android Studio 看 Logcat

  1. 開啟底部 Logcat 工具視窗。
  2. 選擇目前裝置與 com.klotski.android process。
  3. 重現問題。
  4. 搜尋 FATAL EXCEPTION、AndroidRuntime、Exception。
  5. 從 stack trace 最上方屬於專案的行號開始看。

命令列 Logcat

adb logcat

adb logcat | findstr com.klotski.android

讀 stack trace 的方法

FATAL EXCEPTION: main
java.lang.NullPointerException
    at com.klotski.android.MainActivity.updateStatus(MainActivity.java:552)
    at com.klotski.android.MainActivity.onGridChanged(MainActivity.java:903)

閱讀順序：

  1. 先看 exception 類型，例如 NullPointerException。
  2. 找第一個屬於你的 package 的行號。

常見錯誤排查

新手遇到錯誤時，先分類：是環境、建置、安裝、執行、畫面，還是資料問題。

症狀 常見原因 處理方式
Gradle Sync 失敗 JDK 不相容、SDK 缺失、plugin 下載失敗。 改用 Android Studio JBR，確認 SDK Manager，重試 Sync。
SDK location not found local.properties 不存在或 SDK path 錯。 用 Android Studio 開專案自動產生，或手動設定 sdk.dir。
adb devices 空白 模擬器未啟動、USB debug 未允許、platform tools path 問題。 重啟 emulator，確認手機授權，執行 adb kill-server / adb start-server。
INSTALL_FAILED_VERSION_DOWNGRADE 手機已有較高 versionCode 的 App。 卸載舊版或提高 versionCode。
App 一開就 crash onCreate 初始化錯誤、resource 找不到、NullPointerException。 看 Logcat 的 FATAL EXCEPTION 和第一個專案行號。
按鈕點了沒反應 listener 沒設、狀態判斷阻擋、View 被覆蓋、正在 busy。 檢查 setOnClickListener、canAcceptCommand()、Logcat。
畫面旋轉後資料遺失 沒有保存狀態，或只保留在 Activity 欄位。 用 SharedPreferences、onSaveInstanceState 或 ViewModel 保存。
模擬器很慢 硬體加速未啟用、RAM 太低、系統映像不適合。 使用 x86_64 / arm64 適合本機架構的映像，調高 RAM，關閉其他重負載程式。
中文亂碼 檔案編碼或命令列輸出編碼不一致。 源碼與文件使用 UTF-8；Java 編譯使用 -encoding UTF-8。
Lint 報硬編碼文字 Java / XML 直接寫 UI 字串。 移到 strings.xml，用 getString() 取用。

排查順序建議

  1. 先確認 Git 工作區，避免不小心混入其他變更。
  2. 重現問題，記下明確步驟。
  3. 看 Logcat 或 Gradle output 的第一個真正錯誤。
  4. 找出是環境、建置、安裝、runtime、UI、資料哪一層。
  5. 做最小修改。
  6. 跑最小相關驗證。
  7. 再跑較廣的 smoke test 或 lint。

後續維護與功能擴充

當 App 可以跑之後，真正的工程工作才開始：穩定、可測、可維護、可發佈。

適合 SlideDo 的後續功能

功能 修改範圍 注意事項
Settings MainActivity 新增 screen；strings.xml 新增文字；SharedPreferences 保存設定。 先做 haptics toggle、theme toggle、sound toggle。
Results screen 把 win dialog 演進成完整結果畫面。 清楚標示 solver-assisted completion 不記錄。
Instrumentation tests 新增 androidTest。 測 Home → Mode Select → Game，save/load，rotation。
CI GitHub Actions 或其他 CI。 跑 JUnit、desktop compile、Android assemble/lint。
Release signing Gradle signing config、keystore、versionCode。 不要提交 keystore 與密碼。
Accessibility content description、觸控尺寸、對比、TalkBack。 自訂 View 需要額外設計可存取性。

維護時的工程習慣

  • 改共用核心前先跑 root JUnit tests。
  • 改 Android UI 後至少跑 assembleDebug、lintDebug、emulator smoke test。
  • 新增畫面文字時更新 strings.xml。
  • 新增保存欄位時同時檢查 save、load、restart、rotation。
  • 新增 solver 或背景工作時確認不阻塞 UI thread，且可取消或避免重複觸發。
  • 新增依賴前先確認它是否真的必要，並了解 license 與 APK size 影響。
  • 發佈前確認版本號、簽章、隱私權、權限、crash 監控與 release notes。

何時重構

新手常以為重構越早越好，其實應看訊號：

  • 同樣的 UI 建立邏輯重複三次以上。
  • MainActivity 太長，新增功能時很難找到位置。
  • 保存欄位越來越多，手寫 parse/flatten 容易出錯。
  • 測試很難寫，因為邏輯和 Android API 綁太緊。
  • 每次改一個畫面，都意外影響其他畫面。

常見問題

整理新手最容易問的 Android 開發問題。

為什麼 SlideDo 用 Java，不用 Kotlin？

因為它本來有 Java 桌面核心，Android 版可以直接共用。新專案若沒有共用 Java 需求， Kotlin 通常是現代 Android 的主流選擇。

為什麼不用 XML layout？

目前畫面數量不多，而且棋盤本身需要自訂繪製。Programmatic UI 讓控制流程集中在 MainActivity。若畫面變多，XML 或 Compose 會更利於維護。

為什麼保存不用 Room database？

SlideDo 目前只需要保存一筆遊戲狀態與少量最佳紀錄，SharedPreferences 已足夠。 若未來要保存大量歷史紀錄、每日關卡、玩家資料，再考慮 Room。

為什麼 Android UI 不直接修改棋盤陣列？

因為棋盤規則、undo、restart、win detection、solver、save/load 都依賴 GameModel。 UI 直接改陣列會破壞單一真相來源。

debug build 可以拿去發佈嗎？

不應該。Debug build 適合本機測試；正式發佈要建立 release build、簽章、版本號、隱私權與測試流程。

我應該先學 Compose 還是傳統 View？

如果你的目標是現代新專案，Compose 很值得學。如果你要讀現有專案、維護 Java app、 或理解 Android 底層 View 事件，傳統 View 仍然很重要。SlideDo 屬於後者的好範例。
